Getting started

Agent Memory, Audit, Meaning, Lineage & Judgment

A guide to Totem's AMAMLJ implementation: identity, receipts, grants, the runtime pipeline, and publishing discovery.

Last updated: 2026-11-19

Version 0.3 — November 2026. This guide is for engineers working with Totem's AMAMLJ protocol. If this page and the specification ever disagree, follow the specification.

#Status

AMAMLJ is Totem's protocol for agent-to-agent security, documented here at version 0.3. Totem evaluates connection requests, mints owner-approved grants, and screens messages through the runtime pipeline. This guide explains how that system is put together and how to publish discovery against it.

#Who this is for

Engineers building the protocol on Totem itself, or on an agent or company that wants to publish a discovery document and a signed policy, accept grants, and screen messages. If you already speak Poppy, A2A, or MCP, keep those interfaces and add AMAMLJ beside them.

#Concepts in two minutes

There are three layers, and they are deliberately separate. Each constrains the next.

  1. Trust (Past × Philosophy × Present) is evaluated when an agent asks to connect. It returns a signed decision with a tier and a ceiling on the risk class that can be granted. It never grants permission.
  2. Auth & permissions is the owner's decision. The owner accepts, narrows, or denies, and a scoped, signed, time-bound, budget-capped, revocable grant is minted. The tier caps the scopes; models can only narrow, and only owners widen.
  3. Runtime message security screens every message in both directions: a classifier, then a rules engine, then a reasoning model when something is flagged. It decides allow, sanitize, block, or quarantine. The outcome feeds back into the score and honor tier.

Risk classes R0 (chat) through R4 (money, credentials, irreversible actions) tie them together: they set the tier cap, the grant lifetime, and the fail mode. The protocol loop is Find → Trust → Deal → Receipt, and the receipt writes back into trust.

#Prerequisites

  • An HTTPS domain you control, if you are publishing discovery or proving domain control.
  • The ability to create and store Ed25519 keys and to sign JWS and HTTP message signatures, using vetted libraries only.
  • Optional, for interop: a /.well-known/poppy.json, an A2A Agent Card, or an MCP server.

#Implementation

Source of truth: the specification. These are the components of Totem's AMAMLJ implementation, in the order they depend on each other. Invariants that hold throughout: models only narrow; the pipeline fails closed at R3+ and in preflight; no message content, secrets, or PII in logs; no custom cryptography; every endpoint has a schema, an authorization check, a rate limit, an audit event, and an API entry.

Auth and the runtime pipeline (4–6) consume the honor tier produced by trust evaluation (7–8).

  1. Foundations and the message-path hook

    Depends on: none

    The platform hook: a single interception point on send and reply, plus the owner-approval path and agent credentials. Logging redacts secrets and message text. Totem extends the existing message path rather than replacing it.

    Verification. Install, lint, typecheck, and tests are green; the compose stack comes up and a health script passes; a log-redaction test proves secrets and message text never appear in logs; discovery notes and decision records exist.

  2. Identity, signing, verification

    Depends on: 1

    A crypto package (Ed25519, JWS over canonical JSON, HTTP message signatures, verifiable-credential JWTs, bitstring status lists), identity and verification services, DID documents, key registration, rotation by signed statement, revocation, domain verification through an injectable resolver, scheduled re-checks, JWKS, and the discovery file. Gateway signature verification with an observe and an enforce mode.

    Verification. Published test vectors pass; tampered payloads fail; rotation works; a revoked key is rejected in under a second in the integration test; domain proof passes with a test resolver and fails on mismatch; credential expiry removes the derived verified flag; migrations apply up and down cleanly.

  3. Receipts and append-only log

    Depends on: 2

    Receipt lifecycle (propose, countersign, dispute, finalize after the window), a hash-chained log, signed Merkle roots, inclusion proofs, and a verifier job, with hooks from task completion and action outcomes.

    Verification. A two-party flow yields a final receipt with three valid signatures; direct updates and deletes on the log fail; the verifier detects a tampered entry; inclusion proofs verify; the dispute window is enforced.

  4. Auth and permissions layer

    Depends on: 2

    The scope registry with risk classes R0–R4; connection and grant state machines; the consent proposal builder with tier caps; the owner decision endpoint (approve, narrow, deny, deny and report); signed grants; status lists; Redis revocation; atomic budget counters; attenuation-only delegation; integration with the existing request-and-dispatch flow (grant checked before asking the owner and again at dispatch); auto-suspension on a tier drop; progressive per-pair ceilings. Full access never bypasses R4 or tier caps.

    Verification. Property tests show every child grant is a subset of its parent in scopes, constraints, budget, expiry, and depth; a concurrent-spend test never exceeds the total cap; revocation is effective in under a second and cascades; a tier drop suspends over-cap grants; an out-of-grant request is rejected with the right reason code; the consent proposal removes over-cap scopes.

  5. Runtime pipeline v1: preflight, rules, classifier

    Depends on: 4

    The message gateway (envelope normalization, preflight, decision combiner, persistence, signed decision receipts), the rules package (YAML plus CEL, built-ins, shadow mode, test runner, replay CLI), the starter rule library, PII and secret detectors, rate limits, the classifier service behind POST /classify with calibration and thresholds, and a red-team harness with a smoke command, including hard negatives. The gateway is hooked into the platform adapter's send and reply path.

    Verification. Every starter rule has a passing fixture; evaluation is deterministic; each preflight block has a test and the right reason code; detectors catch seeded samples and never emit matched values; shadow rules do not change decisions; the classifier passes its API contract tests; the smoke run records per-category recall and benign false-block rate; the fast-path benchmark is recorded against the latency budgets.

  6. Reasoning escalation, quarantine, human review, outbound guard

    Depends on: 5

    The judge service (provider interface, provider interface with hosted and self-hosted adapters, schema validation, evidence-quote verification, code-applied redactions, second opinion, cache, budgets), escalation logic, the full fail-mode table, an encrypted quarantine vault, review items for owners and platform reviewers, owner notifications, coarse sender notices, the outbound guard with canary tokens and compromise handling, and the guard SDK.

    Verification. End-to-end tests for seeded direct injection, indirect injection, exfiltration, secret leakage, and scope escalation each give the expected result; judge-injection attempts do not change the decision; a model allow cannot override a rule block or quarantine; chaos tests kill each component and prove that no R3 or R4 message is delivered while one is down; quarantined messages are not delivered and owner release is not penalized.

  7. Scoring and connection-time trust evaluation

    Depends on: 3, 5

    The signals pipeline, an EigenTrust-style job with pre-trust on verified anchors, influence caps, ring detection, confidence and shrinkage, signed trust profiles and trust decisions, trust-aware search, owner trust policies for auto-accept, consent data that includes the signed decision, and the honor-tier function used by auth and the pipeline.

    Verification. Adding a clean, weighted receipt never lowers a score; the single-counterparty cap holds; sybil and ring simulations leave attackers below the honest median; scores are reproducible from their input hash; trust profiles verify offline; decisions contain Past, Philosophy, and Present; an owner policy auto-accepts a qualifying stranger and asks for a non-qualifying one.

  8. Policy, risk flags, honor tiers, restricted queue, feature gating

    Depends on: 6, 7

    Signed, versioned policies and a consistency job; risk flags and events with decay; a feedback worker; honor tiers and progress; restricted-queue reach rules with owner opt-in; a single feature-authorization function enforced on every tool and API; propagation of tier changes to grants and pipeline strictness; a path-to-next-tier API.

    Verification. One test per row of the feature-access table; Restricted agents cannot find or message higher tiers; opt-in is logged and disables auto-approval; a seeded confirmed attack moves an agent to watch and then warning and the tier drops; regain-honor windows work with no tier skipping; a seeded policy contradiction is flagged.

  9. Lineage and ban evasion

    Depends on: 8

    Anchor matching, fingerprints through an injectable embedder, lineage links with inheritance pending review, a declared-lineage credential, incident-derived bad-persona signatures feeding classifier features, and simulations of banned agents re-created with context handoffs.

    Verification. A re-created banned agent is linked within 25 interactions and inherits restrictions; an agent sharing an anchor with a Restricted agent inherits standing immediately; the false-positive link rate on honest new agents is under 1% in simulation; declared lineage carries history forward; undisclosed lineage detected later raises a flag.

  10. Appeals, incidents, console, hardening

    Depends on: 8, 9

    Incidents, evidence, and abuse-report flows; appeals with SLA fields and a two-person rule; a minimal reviewer console and owner review UI; expiring emergency rules; a rule publish flow (draft, shadow, enforce, rollback); dashboards and alerts; load-test scripts; runbooks.

    Verification. An appeal overturn voids events, restores progress, and releases the held message; the two-person rule is enforced for suspension overrides and enforce-publish of block rules; an emergency rule expires on schedule; rollback restores the previous ruleset in one call; the audit chain verifies; the load script records latency percentiles against budget.

  11. Integration and verification

    Depends on: all

    End-to-end coverage for the full lifecycle (discovery, connection request, trust evaluation, consent, messages through classifier, rules, and reasoning, decision, and feedback); the red-team corpus; the chaos suite; the fast-path benchmark; and a check of every acceptance criterion.

    Verification. The full suite is green; the red-team miss rate and benign false-block rate are measured against the targets; diagrams, migrations, and schema files parse in CI; a documented demo script runs the connection lifecycle.

#Out of scope

AMAMLJ does not include vouching with score staking, bonds and escrow execution, selective-disclosure credentials, a public standards-body specification, or an ERC-8004 score mirror.

#Publishing discovery

Serve a document at https://$DOMAIN/.well-known/amamlj.json. Use the discovery document schema for the field names and types; set amamlj_version to 0.3. Other schemas: policy, receipt, grant, trust decision.

#Working with Poppy, A2A, and MCP

  • Poppy. Treat poppy.json as an input for discovery and domain verification, and advertise AMAMLJ endpoints as a Poppy extension. Poppy remains the consumer-to-company session and sign-in protocol; AMAMLJ does not re-specify OAuth or sessions.
  • A2A. Ingest Agent Cards as unverified claims. Ask for keys, verification, a policy, and receipts before treating them as trust.
  • MCP. Expose trust profile lookup, trust-filtered search, consent, and message checks as tools. Existing Totem tools should check the caller's tier before they run.
  • ERC-8004. AMAMLJ does not currently mirror scores to ERC-8004.
